# timeoptic

โมดูลคลังสินค้าและต้นทุน FIFO ของร้านแว่น — แยก backend (PHP) กับ frontend (Next.js)

โปรเจกต์นี้กำลังเขียนขึ้นใหม่จาก `optical-inventory` (Next.js เต็มตัว) เพื่อให้
merge เข้ากับระบบหน้าร้านของทีมที่เป็น PHP ได้ **ของเดิมยังใช้งานได้ปกติ**
และยังเป็นตัวอ้างอิงว่าความสามารถไหนที่ยังต้องย้ายมา

---

| ส่วน | สถานะ |
|---|---|
| `Db` · `Env` · `Errors` · `Roles` · autoloader | เสร็จ |
| `Service\Stock` — ตัด/ของเสีย/คืน/เช็คยอด | เสร็จ · 31 เทสต์ผ่าน |

| frontend Next.js | ยังไม่ได้ทำ |

**ยังเปิดหน้าเว็บไม่ได้** สิ่งที่รันได้ตอนนี้คือเทสต์กับ migration

## สิ่งที่ต้องมีในเครื่อง

- **PHP 8.4** ลงด้วย `winget install --id PHP.PHP.8.4`
  ต้องมี `php.ini` ที่เปิด `pdo_mysql`, `mbstring`, `openssl`, `intl`
  และตั้ง `date.timezone = Asia/Bangkok` — ฐานข้อมูลเก็บ `DATETIME` ที่ไม่มี timezone
  ถ้า PHP กับฐานข้อมูลคนละโซน วันที่รับเข้าล็อตจะเลื่อนไปหนึ่งวัน
- **ไม่ต้องใช้ Composer** autoloader เขียนเองอยู่ใน `api/src/bootstrap.php`
  ตอน merge เข้าโปรเจกต์ที่มี Composer อยู่แล้ว ให้ลบไฟล์นั้นทิ้ง
  แล้วเพิ่ม `"Optic\\": "api/src/"` ลง autoload map แทน — ที่เหลือไม่ต้องแก้

`php` ไม่เจอหลังลงเสร็จ ให้เปิด terminal ใหม่ (PATH เพิ่งถูกแก้)

**เปลี่ยนก่อนใช้งานจริง** แอปนี้เปิดอยู่บนวง LAN ของร้าน

`admins` เป็นตารางคนเดียวของทั้งระบบแล้ว — ตอนนี้มี 6 คน คือเจ้าของร้าน 1 คน
ที่ล็อกอินได้ กับพนักงาน 5 คนที่นำเข้ามาจาก `employees` ซึ่ง **ไม่มีรหัสผ่าน**
เพราะยังไม่จำเป็นต้องล็อกอิน แต่ต้องมีตัวตนไว้ให้บันทึกได้ว่าใครทำรายการ

`job_title` (เช่น `technician`, `reception,sales`) บอกว่าทำงานอะไร
`role` (`owner` / `accountant` / `staff`) บอกว่าทำอะไรในระบบได้
**สองอย่างนี้ไม่เกี่ยวกัน** และห้ามเอา `job_title` มาตัดสินสิทธิ์ — คนที่มีคำว่า
`admin` อยู่ใน job title ไม่ได้แปลว่าเป็นเจ้าของร้าน

## ฐานข้อมูล

`.env` ที่ราก ชี้ไป MariaDB 10.4 บนเครื่องในร้าน (`192.168.1.107`)
เป็นฐานข้อมูล **เดียวกัน** กับที่ `optical-inventory` ใช้ และเดียวกับระบบหน้าร้าน

โมดูลนี้เป็นเจ้าของหกตาราง — `categories` `suppliers` `products` `stock_lots`
`inventory_logs` `admins` — ที่เหลือประมาณ 35 ตารางเป็นของระบบหน้าร้าน

**ไม่มี foreign key ข้ามไปมาระหว่างสองฝั่งแม้แต่เส้นเดียว** สองระบบแยกกันด้วย
วินัย ไม่ใช่ด้วย constraint มีเทสต์คุมข้อนี้ไว้ใน `00-foundation.test.php`
ถ้า migration ของฝั่งไหนเผลอสร้าง FK ข้ามมา เทสต์จะแดงทันที

### สองอย่างที่ห้ามลืมเวลาเขียนโค้ดแตะฐานข้อมูลนี้

1. **`sql_mode` ของเซิร์ฟเวอร์ไม่มี `STRICT_TRANS_TABLES`**
   `Db::conn()` จึงบังคับเปิดเองระดับ session ถ้าไม่เปิด การลบ `remaining_qty`
   จนติดลบจะถูก **ปัดเป็น 0 เงียบ ๆ** แทนที่จะ error แล้วสต็อกจะเพี้ยนโดยไม่มีใครรู้
   ห้ามไปเปลี่ยนระดับ global เพราะระบบหน้าร้านใช้เซิร์ฟเวอร์เดียวกัน
   และอาจพึ่งพฤติกรรมหลวม ๆ นั้นอยู่

2. **MariaDB 10.4 ไม่มีชนิด JSON จริง และ `->>` ใช้ไม่ได้**
   `products.attributes` เป็น `LONGTEXT` ต้องเขียน
   `JSON_UNQUOTE(JSON_EXTRACT(col, '$.path'))` เท่านั้น — `->>` ตอบ error 1064

## หลักที่โค้ดยึด

**FIFO เป็นหน้าที่ของ `Service\Stock` ไม่ใช่ของผู้เรียก**
ผู้เรียกบอกแค่ว่าสินค้าอะไร กี่ชิ้น การเลือกล็อตคือการตัดสินใจทางบัญชี
เพราะต้นทุนต่อชิ้นผูกอยู่กับล็อต ไม่ใช่กับสินค้า

**ทุกคำขอที่เปลี่ยนสต็อกต้องมีกุญแจกันซ้ำ**
ช่างกดสองทีหรือเน็ตกระตุกเป็นเรื่องปกติ กุญแจต้องมีอยู่ก่อนยิง และตอนยิงซ้ำ
ต้องเป็นค่าเดิม — `job:1042:left` จากใบสั่งงาน หรือ `adhoc:<uuid>` จากฟอร์ม
**คำขอที่ถูกปฏิเสธจะไม่จองกุญแจไว้** เพราะ "ของหมด" วันนี้ไม่ได้แปลว่าหมดตลอดไป

**ของเสียไม่ใช่ต้นทุนขาย**
เลนส์ที่ช่างตัดเสียออกจากสต็อกเหมือนการขาย แต่บันทึกเป็น `SCRAP`
ถ้ากองรวมใน `OUT` ต้นทุนขายจะบวมและตอบไม่ได้ว่าเดือนนี้เสียไปกี่ชิ้น

**สินค้าสั่งตัด (`is_custom_made`) ไม่มีสต็อกให้ตัด**
ตอบ `409 custom_made` เสมอ ไม่ใช่ `404` และไม่ใช่ `on_hand: 0` เฉย ๆ
เพราะมันไม่ได้ "หมด" — มันไม่เคยมี ตอนนี้ 6 จาก 29 รายการเป็นแบบนี้

**ชื่อสินค้าประกอบจากสเปก ไม่ใช่พิมพ์เอา**
`Catalog::composeName()` เป็นที่เดียวที่ตัดสินว่าสินค้าชื่ออะไร — แบรนด์ · รุ่น
(`attributes.model`) · แล้วตามด้วยสิ่งที่ทำให้สองตัวของรุ่นเดียวกันต่างกัน
เลนส์คือ Coating · Index · SPH · CYL · ADD **ใส่เฉพาะค่า ไม่ใส่คำว่า SPH/CYL**
และใช้ `-` ธรรมดาไม่ใช่เครื่องหมายลบยูนิโค้ด เพราะชื่อนี้ถูกเก็บ ถูกค้น และถูกพิมพ์หา
ฟอร์มเรียก `GET /api/products/compose-name` เพื่อแสดงตัวอย่างชื่อ ไม่ได้คำนวณเองในเบราว์เซอร์
— สองสำเนาของกฎเดียวคือโอกาสให้ตัวอย่างกับที่บันทึกจริงไม่ตรงกัน
**ชื่อที่พิมพ์เองชนะเสมอ** ส่งชื่อว่างมาคือสั่งให้ตั้งให้

**จำนวนขั้นต่ำเก็บไว้ ยอดที่ใช้เตือนคำนวณสด**
`products.min_stock` คือระดับที่เจ้าของร้านตั้ง — 0 แปลว่า **ไม่เตือน** ไม่ใช่ "ขั้นต่ำศูนย์"
ส่วน "ตอนนี้เหลือเท่าไร" อ่านจาก `stock_lots` ทุกครั้งที่ถาม ไม่มีคอลัมน์ไหนเก็บผลไว้
เงื่อนไข "ต่ำกว่าขั้นต่ำ" เขียนครั้งเดียวที่ `Inventory::LOW_STOCK` แล้วใช้ซ้ำสามที่
(ตัวกรอง · ตัวเลขบนชิป · ตัวเลขบนหน้าสรุป) เพราะสามสำเนาคือสามโอกาสให้ตัวเลขไม่ตรงกัน

**Invariant เดียวที่ต้องจริงตลอด**
`stock_lots.remaining_qty` ของทุกล็อต = ผลรวม `inventory_logs.quantity` ของล็อตนั้น
มีเทสต์คุมไว้ และใช้เป็น acceptance test ของการย้ายระบบได้เลย:

```sql
SELECT l.lot_number, l.remaining_qty, COALESCE(SUM(g.quantity), 0) AS ledger
FROM stock_lots l LEFT JOIN inventory_logs g ON g.lot_id = l.id
GROUP BY l.id HAVING l.remaining_qty <> ledger;
```

ต้องคืน 0 แถวเสมอ

## โครงไฟล์

```
timeoptic/
  .env                     ชี้ฐานข้อมูล ใช้ร่วมกับ frontend
  api/
    bin/migrate.php        รัน .sql ในโฟลเดอร์ migrations ไฟล์ละครั้ง
    migrations/*.sql       เปลี่ยนโครงสร้างด้วย SQL ที่เขียนมือ ทบทวนได้
    src/
      bootstrap.php        autoloader + โหลด .env
      Env.php              อ่าน .env และแยก DATABASE_URL
      Db.php               PDO + strict mode + tx() ที่ซ้อนกันได้
      Errors.php           ApiError พร้อม reason ที่โปรแกรมอ่านได้
      Roles.php            กฎว่าใครทำอะไรได้
      Service/Stock.php    FIFO · กันซ้ำ · ของเสีย · คืนของ
    tests/
      harness.php          ตัวช่วย assert + withRollback
      run.php              ตัวรัน
      *.test.php
```
