# ระบบรายงาน — ไฟล์ไหนอยู่ตรงไหน เก็บอะไร ทำอะไร

ระบบนี้มีรายงาน **สองก้อนที่ไม่เกี่ยวกัน** อย่าเอามาปนกัน

| ก้อน | เส้นทาง | ใครอ่าน |
|---|---|---|
| รายงานวิเคราะห์ยอดขาย (7 หน้า) | `/reports` · `/api/reports/*` | เจ้าของร้าน / แอดมิน |
| เอกสารประจำวัน + ใบพิมพ์ | `/api/reports/daily-closed` ฯลฯ | พนักงานหน้าร้าน |
| รายงานสต็อก (คนละแอป) | `/stock/dashboard` · `stock/api` | คนคุมคลัง |

---

## 1. `api/routes/` — ประตูของ API

| ไฟล์ | เก็บอะไร |
|---|---|
| **`analytics.php`** (606 บรรทัด, ไฟล์ใหม่) | 7 เส้นทางของรายงานวิเคราะห์ — `overview` · `main-process` · `pos` · `payments` · `profit` · `employees` · `channels` · ทุกเส้นรับพารามิเตอร์ชุดเดียวกัน `?from=&to=&channel=all\|main\|pos` · ไม่มี SQL อยู่ในไฟล์นี้เลย (ยกเว้นตาราง `bookings` ในหน้า channels) หน้าที่ของมันคือ "เอาบิลจาก SalesReport มานับคนละแบบ" แล้วส่ง JSON |
| **`reports.php`** (181 บรรทัด, ของเดิม) | เอกสารที่พนักงานกดใช้ประจำวัน — ปิดยอดรายวัน (`daily-closed`) · รายรับรายเดือน (`income-by-month`) · เช็คลิสต์สต็อก (`checklist`) · ป้ายราคา (`stock-labels`) · ของค้างสต็อก (`unsold-stock`) · ใบสั่งตัดแว่น (`order/:id`) · ใบค่าสายตา (`prescription/:id`) · ภาระงาน (`workload`) |
| `dashboard.php` | ตัวเลขบนหน้าแรก (คนละชุดกับรายงาน) |
| `cashflow.php` | รายรับ/รายจ่ายที่คีย์มือ — เป็นแหล่งข้อมูล ไม่ใช่รายงาน |

> **ทำไมแยกสองไฟล์** — คนละคนอ่าน คนละเวลา และแทบไม่เคยแก้พร้อมกัน · แต่ยังใช้คำนำหน้า `/api/reports/` เหมือนกันเพื่อให้ติดด่านแอดมินอันเดียวกัน

## 2. `api/services/` — ตรรกะการนับ

| ไฟล์ | เก็บอะไร |
|---|---|
| **`SalesReport.php`** (710 บรรทัด) | **ที่เดียวที่ตัดสินว่า "ยอดขาย" แปลว่าอะไร** · ทั้ง 7 หน้าอ่านบิลจากที่นี่ที่เดียว ตัวเลขจึงตรงกันเสมอ<br>· `range()` ตีความ from/to/channel (ส่งกลับหัวกลับหางก็สลับให้)<br>· `mainBills()` งานตัดแว่นจาก `custom_orders` · `posBills()` ขายหน้าร้านจาก `pos_sales` + `sales` (ของเดิม ติดธง `src='legacy'`)<br>· `receipts()` เงินที่รับจริงจาก `payments` / `pos_payments` — นับด้วย `paid_at`<br>· `totals()` `customers()` `groupBy()` `daily()` `margin()` `bounds()` `outstandingAllTime()`<br>· `bucketFor()` เลือกความละเอียดแกนเวลา: ≤45 วัน = รายวัน · ≤210 วัน = รายสัปดาห์ · เกินนั้น = รายเดือน |
| **`CaseSource.php`** (298 บรรทัด) | จัดว่าลูกค้ารายนี้มาจากไหน (SightFirst / ออนไลน์ / เดินเข้าร้าน) จากช่องทางที่ติ๊ก + โน้ตของเคส · ผลเก็บลง `cases.customer_category` ซึ่งหน้า "ช่องทางลูกค้า" อ่านต่อ |

**นิยามสำคัญสองคำที่ห้ามยุบเป็นคำเดียว** (อยู่ในหัวไฟล์ `SalesReport.php`)

```
ยอดขาย    = ราคาที่ตกลงในบิล → นับด้วยวันที่เปิดบิล   (6 หน้าใช้ราง นี้)
ยอดรับเงิน = เงินที่เข้ามาจริง  → นับด้วย paid_at      (หน้า "การรับเงิน" ใช้รางนี้)
```

## 3. `api/index.php` — ด่านสิทธิ์

บรรทัด ~117 `ADMIN_PREFIXES` กัน `/api/reports` ทั้งคำนำหน้าไว้ให้แอดมินขึ้นไปเท่านั้น — เส้นทางรายงานที่เขียนเพิ่มวันหน้าถูกกันเองโดยไม่ต้องเติมโค้ดตรวจสิทธิ์ · การซ่อนเมนูฝั่งหน้าเว็บเป็นแค่มารยาท ด่านจริงอยู่ที่นี่ · ระดับนี้เท่ากับ `Roles::seeCost()` พอดี ต้นทุนจึงไม่รั่ว

## 5. `frontend-next/app/(frontdesk)/reports/` — หน้าเว็บ 7 หน้า

```
reports/
├─ layout.jsx        โครงร่วม: AdminOnly + หัวเพจ + แถบแท็บ 7 แท็บ
│                    แท็บพาตัวกรองไปด้วย (กดข้ามหน้าแล้วช่วงวันที่ไม่หาย)
├─ page.jsx          ภาพรวม     KPI 5 ตัว · โดนัทสองช่องทาง · กราฟยอดตามช่วง
├─ main-process/     งานตัดแว่น  KPI + กราฟตามเลนส์/พนักงาน + ตารางรายเคส
├─ pos/              ขายหน้าร้าน KPI (นับเป็น "ชิ้น") + กราฟหมวดสินค้า + ตารางบิล + ใบที่ยกเลิก
├─ channels/         ช่องทางลูกค้า  รู้จักร้านจากไหน · conversion · ที่มาลูกค้า · ช่องทางที่จองเข้ามา
├─ payments/         การรับเงิน   โดนัทช่องทางชำระ + การ์ดผ่อนชำระ + กราฟเงินเข้า (paid_at)
├─ profit/           กำไร        ต้นทุนกรอบ/เลนส์จากล็อต · แท่งซ้อน ต้นทุน/กำไร · POS แจ้งว่าไม่มีต้นทุน
└─ employees/        พนักงาน     รวมงานสองฝั่งของคนเดียวกัน (employees ↔ admins.employee_id)
```

## 9. ตารางในฐานข้อมูลที่รายงานอ่าน

| ตาราง | ใช้ทำอะไร |
|---|---|
| `custom_orders` | บิลงานตัดแว่น + `frame_product_id` / `lens_product_id` ที่ชี้ไป **ล็อต** เพื่อดึงต้นทุน |
| `pos_sales` · `pos_sale_items` · `pos_payments` | ขายหน้าร้าน (ยกเลิกแล้วไม่นับเป็นยอด แต่นับให้เห็น) |
| `sales` | การขายยุคก่อนมี POS — ยังมีเงินจริงอยู่ ต้องนับรวม ติดธง `legacy` |
| `payments` | เงินที่รับจริงของฝั่งงานตัดแว่น (ยอดชำระเชื่อ ledger นี้ ไม่เชื่อ `custom_orders.deposit`) |
| `cases` | `referral_source` (รู้จักร้านจากไหน) · `customer_category` (ที่มาลูกค้า) |
| `bookings` | ช่องทางที่ติดต่อเข้ามา + แปลงเป็นเคสได้กี่ % (ตารางอาจไม่มีในฐานที่เพิ่งติดตั้ง — โค้ดกันไว้แล้ว) |
| `employees` ↔ `admins.employee_id` | เชื่อมคนขายสองระบบให้เป็นแถวเดียว |
| `v_case_board` · `v_stock_lot` · `list_len_type` | สถานะเคส · ต้นทุนต่อหน่วยของล็อต · ป้ายประเภทเลนส์ |

## ยังไม่มี

* รายงานรวมหลายชั้นแบบ `superrptOrder` / `superrptSales` ของ Access เดิม
* ต้นทุนฝั่ง POS — `pos_sale_items` ไม่มีคอลัมน์ต้นทุน หน้ากำไรจึงส่ง `has_cost=false` ออกไปตรง ๆ แทนที่จะเดา
* หน้าเว็บที่เรียก `reports.php` — ทั้ง `daily-closed` · `income-by-month` · `checklist` · `stock-labels` · `unsold-stock` · `workload` · `order/:id` · `prescription/:id` ยังไม่มีหน้าไหนใน `frontend-next` เรียกใช้เลย (หน้าพิมพ์ที่ `print/order` กับ `print/prescription` ดึงจาก `/api/orders` และ `/api/cases` ตรง ๆ) · API ก้อนนี้จึงเป็นของที่ยกมาจากแอปเดิมและยังไม่ได้ต่อกลับ
