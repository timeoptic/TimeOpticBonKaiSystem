# Employee เป็นข้อมูลหลัก · บัญชีเข้าใช้งานผูกกับพนักงานเสมอ

วันที่ 8 กันยายน 2026 · สาขา `frontdesk-ui-pass-and-e2e`

## โจทย์

ทุกวันนี้ระบบเก็บ "คน" ไว้สองที่ที่ไม่รู้จักกัน

- `employees` — พนักงานร้าน มาจากการนำเข้า Access · หน้าจอ `/employees` · ใช้เป็นคนขาย
  ในเคสตัดแว่นและใบขาย (`sales.employee_id`, `case_events.employee_id`)
- `admins` — บัญชีเข้าใช้งานและสิทธิ์ · หน้าจอ `/users` · ใช้เป็นคนคีย์และคนรับของ
  (`inventory_logs.created_by`, `issued_to_admin_id`, `pos_sales.created_by`, …)

คอลัมน์ `admins.employee_id` มีอยู่แล้วและเป็น UNIQUE แต่ **ว่างทั้ง 12 แถว** — รายงาน
ผลงานพนักงาน (`GET /api/reports/employees`) ที่เชื่อมสองฝั่งด้วยคอลัมน์นี้จึงเทงานฝั่ง POS
ลงแถว "ไม่ระบุพนักงาน" ทั้งหมด และการรับคนใหม่หนึ่งคนต้องคีย์สองที่ ปิดคนที่ลาออกก็ต้องปิดสองที่

เป้าหมาย: **พนักงานคือข้อมูลหลัก บัญชีเป็นของที่ห้อยอยู่กับพนักงาน** จัดการคน สิทธิ์
และการเข้าใช้งานจากข้อมูลชุดเดียว

## กฎที่ระบบต้องบังคับหลังงานนี้

1. ทุกแถวใน `admins` ต้องมี `employee_id` — บังคับด้วย NOT NULL + FOREIGN KEY ไม่ใช่ด้วยโค้ด
2. พนักงานหนึ่งคนมีได้อย่างมากหนึ่งบัญชี — บังคับด้วย UNIQUE ที่มีอยู่แล้ว
3. เพิ่มพนักงานหนึ่งคน ได้แถวใน `admins` หนึ่งแถวทันที โดยยังไม่มี username → "ยังไม่มีบัญชี"
4. ชื่อที่แสดงและหน้าที่ มาจาก `employees` เสมอ · `admins.display_name` / `job_title`
   เป็นสำเนาที่ระบบเขียนตามให้ ไม่ใช่ช่องที่คนกรอก
5. ปิดใช้งานพนักงาน → บัญชีถูกปิดตามทันที · **เปิดพนักงานกลับ ไม่เปิดบัญชีคืน**
6. ลบแถวใน `admins` ไม่ได้อีกต่อไป — สิ่งที่ทำได้คือ "ยกเลิกบัญชีเข้าใช้งาน" ซึ่งล้าง
   username กับรหัสผ่าน แต่เก็บแถวไว้ให้ประวัติอ่านชื่อได้

ข้อ 5 มีผลจริงเพราะ `Optic\Auth::login()` ปฏิเสธทั้ง `is_active = 0` และ
`password_hash IS NULL` อยู่แล้ว — ไม่ต้องเพิ่มด่านใหม่

## Migration — `stock/api/migrations/027_employee_is_master.sql`

รันด้วย `stock/run.ps1 migrate` เหมือนไฟล์อื่น ทุกคำสั่งทำงานอยู่ในฐาน จึงไม่มีข้อความไทย
วิ่งผ่าน client (กับดัก `mysql.exe -e` ที่แปลงไทยเป็น `?`)

```
0. ลบแถวขยะ id 163 (username 'employees' · display_name 'employees' · มีรหัสผ่าน
   เข้าระบบได้จริง · สร้าง 26 ส.ค. 2026 · ไม่มีประวัติสักรายการ)
   ก่อนลบ เขียนค่าทั้งแถวไว้เป็น comment ในไฟล์ migration เป็นสำเนา

1. สร้างพนักงานให้บัญชี 11 แถวที่เหลือ
   ALTER TABLE employees ADD COLUMN _from_admin INT UNSIGNED NULL;
   INSERT INTO employees (employee_name, roles, active, _from_admin)
     SELECT LEFT(display_name,120), LEFT(job_title,200), is_active, id
     FROM admins WHERE employee_id IS NULL;
   UPDATE admins a JOIN employees e ON e._from_admin = a.id SET a.employee_id = e.id;
   ALTER TABLE employees DROP COLUMN _from_admin;

   ผูกกลับด้วยคอลัมน์ชั่วคราว ไม่ใช่ด้วยชื่อ — ชื่อซ้ำกันได้ และ INSERT…SELECT
   ไม่คืน id ของแต่ละแถวมาให้

2. สร้างแถวเงาใน admins ให้พนักงาน 13 คนที่ยังไม่มี
   INSERT INTO admins (employee_id, display_name, job_title, role, is_active)
     SELECT e.id, e.employee_name, LEFT(e.roles,120), 'sales', e.active
     FROM employees e LEFT JOIN admins a ON a.employee_id = e.id
     WHERE a.id IS NULL;

   role = 'sales' เป็นค่าที่ไม่มีความหมายจนกว่าจะมีการสร้างบัญชี — แถวที่ไม่มี
   username เข้าระบบไม่ได้ไม่ว่าจะถือ role อะไร หน้าจอจึงไม่แสดง role ของแถวพวกนี้

3. ปิดกฎ
   ALTER TABLE admins MODIFY employee_id INT UNSIGNED NOT NULL;
   ALTER TABLE admins ADD CONSTRAINT fk_admins_employee
     FOREIGN KEY (employee_id) REFERENCES employees (id);
```

ผลลัพธ์: 24 พนักงาน ↔ 24 บัญชี ผูกกัน 1:1 ครบทุกแถว · เข้าระบบได้จริง 6 บัญชี (owner
กับบัญชีทดสอบ 5 บัญชี) · อีก 18 แถวเป็น "ยังไม่มีบัญชี" คือพนักงาน 13 คนที่เพิ่งได้แถวเงา
บวกบัญชีเดิม 5 แถวที่ไม่เคยมีชื่อผู้ใช้ (ไทม์ · แนน · ช่างเอก · พี่หนู · ช่างทดสอบ 5bdi7)

**ผลข้างเคียงที่ยอมรับแล้ว:** บัญชีทดสอบ 5 บัญชีกลายเป็นพนักงาน 5 คนชื่อ "ทดสอบ · …"
และไปโผล่ในช่องเลือกพนักงานทุกหน้าของหน้าร้าน ชื่อขึ้นต้นด้วย "ทดสอบ ·" อยู่แล้วจึงแยกออกจาก
คนจริงได้ และเจ้าของร้านปิดใช้งานเองได้ที่หน้าพนักงานเมื่อไม่ต้องการ — ไม่ใส่กฎพิเศษใน API
เพราะกฎที่อิงข้อความในชื่อจะพังวันที่มีคนชื่อจริงขึ้นต้นแบบนั้น

**ย้อนกลับ:** `ALTER TABLE admins DROP FOREIGN KEY fk_admins_employee, MODIFY employee_id
INT UNSIGNED NULL;` แล้วลบแถวพนักงานที่ migration สร้างขึ้น — เขียนไว้ท้ายไฟล์เป็น comment
สำรองฐานด้วย `mysqldump --default-character-set=utf8mb4 --single-transaction` ก่อนรัน

## API

### `stock/api/src/Service/Users.php` — ยังเป็นที่เดียวที่ตัดสินเรื่องสิทธิ์

| เมธอด | เปลี่ยนเป็น |
|---|---|
| `list(string $role)` | `JOIN employees` · เพิ่มคีย์ `employeeId` `employeeName` `employeeActive` `hasAccount` ในผลลัพธ์ · `hasAccount = username IS NOT NULL AND password_hash IS NOT NULL` · เรียงพนักงานที่ทำงานอยู่ก่อน แล้วมีบัญชีก่อน แล้วชื่อ |
| `create()` | **ลบทิ้ง** แทนด้วย `grantAccount(int $employeeId, array $req, string $actorRole)` |
| `update(int $id, …)` | เลิกรับ `display_name` / `job_title` · รับแค่ `username` `role` `is_active` · ปฏิเสธ `is_active = 1` ถ้าพนักงานคนนั้นลาออกแล้ว |
| `delete()` | **ลบทิ้ง** แทนด้วย `revokeAccount(int $id, string $actorRole, int $actorId)` |
| `setPassword()` | ไม่เปลี่ยน (ยังปฏิเสธแถวที่ไม่มี username เหมือนเดิม) |
| `pickable()` | ไม่เปลี่ยนโค้ด — ผลลัพธ์กว้างขึ้นเองเพราะทุกพนักงานมีแถวใน `admins` แล้ว |
| — | เพิ่ม `ensureFor(int $employeeId, string $name, ?string $jobTitle, bool $active): int` — สร้างแถวเงา idempotent |
| — | เพิ่ม `syncFromEmployee(int $employeeId, string $name, ?string $jobTitle, bool $active, int $actorId): void` — เขียนสำเนาชื่อ/หน้าที่ และปิดบัญชีเมื่อพนักงานถูกปิด |

`grantAccount()` ปฏิเสธเมื่อ: พนักงานไม่มีอยู่ · พนักงานลาออกแล้ว · มีบัญชีอยู่แล้ว ·
ชื่อผู้ใช้ซ้ำ · ไม่ได้ส่งรหัสผ่าน · ตั้ง role สูงกว่าตัวเอง (กฎ `Roles::canGrant` เดิม)

`revokeAccount()` ตั้ง `username = NULL, password_hash = NULL` แล้วคง `is_active` ไว้ตามพนักงาน ·
ยังกันสองอย่างเดิม: ยกเลิกบัญชีตัวเองไม่ได้ · ยกเลิกบัญชีเจ้าของร้านที่ใช้งานได้คนสุดท้ายไม่ได้ ·
และยังกันการแตะบัญชีที่ role สูงกว่าตัวเอง (`requireReach`)

`syncFromEmployee()` เมื่อ `$active === false` ต้องปฏิเสธก่อนเขียน ถ้าบัญชีนั้นคือ
`$actorId` เอง หรือเป็นเจ้าของร้านที่ใช้งานได้คนสุดท้าย — ใช้รหัสข้อผิดพลาดเดียวกับที่
`update()` ใช้อยู่ (`self_lockout` / `last_owner`) เพื่อไม่ให้มีคำอธิบายสองสำนวนสำหรับกฎเดียวกัน

### เส้นทาง `stock/api/public/index.php`

- `GET  /api/users` — คงเดิม
- `POST /api/users` — **ลบ** แทนด้วย `POST /api/employees/{id}/account` → `grantAccount()`
- `POST /api/users/{id}/update` — คงเดิม (body เปลี่ยน)
- `POST /api/users/{id}/password` — คงเดิม
- `POST /api/users/{id}/delete` — **ลบ** แทนด้วย `POST /api/users/{id}/revoke` → `revokeAccount()`

### `api/routes/employees.php` (ฝั่งหน้าร้าน)

โค้ดฝั่งคลังถูก `require` เข้ามาแล้วใน `api/index.php` เส้นทางพวกนี้จึงเรียก
`Optic\Service\Users` ตรง ๆ ได้ **และต้องเรียก — ห้ามเขียนตาราง `admins` เอง** ไม่งั้นจะมี
สองที่ที่ตัดสินเรื่องบัญชี ซึ่งเป็นสิ่งเดียวที่คอมเมนต์หัว `users/page.jsx` ห้ามไว้

**ช่องโหว่ที่ต้องปิดไปพร้อมกัน:** ทั้งสามเส้นทางนี้ไม่มีด่านตรวจสิทธิ์เลยในวันนี้ — `AdminOnly`
เป็นแค่การซ่อนเมนูฝั่งหน้าเว็บ ใครยิง `PUT /api/employees/:id` ตรง ๆ ก็แก้ได้ ตราบใดที่การแก้
พนักงานยังแก้ได้แค่ชื่อกับสถานะในรายชื่อ ความเสียหายจำกัด แต่หลังงานนี้การปิดพนักงานหนึ่งคน
คือการปิดสิทธิ์เข้าระบบของเขา จึงต้องใส่ `Auth::require()` + `Roles::require(Roles::manageAdmins(...))`
ที่ POST กับ PUT และ `Auth::require()` ที่ GET · ตรวจแล้วว่าช่องเลือกพนักงานของหน้าอื่น ๆ
อ่านจาก `/api/meta` ไม่ใช่ `/api/employees` การปิดเส้นทางนี้จึงไม่กระทบหน้าอื่น

- `GET /api/employees` — เพิ่มคอลัมน์สรุปบัญชีจาก `LEFT JOIN admins` (`username`, `role`,
  `account_active`) ให้หน้าพนักงานแสดงได้โดยไม่ต้องยิงสอง endpoint
- `POST /api/employees` — INSERT พนักงาน แล้ว `Users::ensureFor()` **ใน transaction เดียว**
  พนักงานที่ไม่มีแถวเงาคือพนักงานที่รับของไม่ได้ ครึ่งทางจึงแย่กว่าไม่สำเร็จเลย
- `PUT /api/employees/:id` — UPDATE พนักงาน แล้ว `Users::syncFromEmployee()` ใน transaction
  เดียวกัน · ถ้า `syncFromEmployee()` ปฏิเสธ ทั้งคำขอต้องล้มและพนักงานต้องไม่ถูกปิด

## หน้าจอ

### `/users` — Users & Roles

- **ไม่มีปุ่ม "เพิ่มผู้ใช้"** แทนด้วยประโยคใต้หัวการ์ด: คนใหม่เพิ่มที่หน้าพนักงาน พร้อมลิงก์ไป
  `/employees` — ปุ่มที่ไม่มีอยู่แล้วอธิบายตัวเองไม่ได้ ต้องมีข้อความบอกว่าไปทำที่ไหนแทน
- คอลัมน์: ชื่อพนักงาน · หน้าที่ · ชื่อผู้ใช้ · สิทธิ์ · สถานะ · รายการที่ทำ · เข้าล่าสุด · ปุ่ม
- สถานะสี่แบบ ไม่ใช่สามแบบ:

  | เงื่อนไข | ป้าย |
  |---|---|
  | พนักงานลาออกแล้ว | `ลาออกแล้ว` (เทา · แถวเทาทั้งแถว) |
  | มีบัญชี · เปิดใช้งาน | `ล็อกอินได้` (เขียว) |
  | มีบัญชี · ปิดใช้งาน | `บัญชีปิดใช้งาน` (เทา) |
  | ไม่มีบัญชี | `ยังไม่มีบัญชี` (เหลือง) |

- คอลัมน์สิทธิ์ว่างสำหรับแถวที่ยังไม่มีบัญชี — `role` ของแถวเงาไม่มีความหมาย แสดงไปก็ชวนเชื่อ
- ปุ่มขวาสุด: **สร้างบัญชีเข้าใช้งาน** เมื่อยังไม่มี · **แก้ไข** เมื่อมีแล้ว · พนักงานที่ลาออกแล้ว
  ไม่มีปุ่มสร้าง (API ปฏิเสธอยู่แล้ว การโชว์ปุ่มที่จะถูกปฏิเสธแน่ ๆ คือการหลอกให้กด)
- เพิ่มช่องค้นหา + ปุ่มกรองสามปุ่มพร้อมตัวนับ (ทั้งหมด · มีบัญชี · ยังไม่มีบัญชี) แบบเดียวกับ
  หน้าพนักงาน — รายชื่อโตจาก 12 เป็น 24 แถวและจะโตตามจำนวนพนักงานต่อไป
- กล่อง **สร้างบัญชี**: ชื่อ/หน้าที่ อ่านอย่างเดียวพร้อมลิงก์ไปแก้ที่หน้าพนักงาน · กรอก
  ชื่อผู้ใช้ · รหัสผ่าน · สิทธิ์
- กล่อง **แก้ไขบัญชี**: ชื่อผู้ใช้ · สิทธิ์ · สถานะ · ตั้งรหัสผ่านใหม่ · ท้ายกล่องเปลี่ยนจาก
  "ลบผู้ใช้" เป็น **"ยกเลิกบัญชีเข้าใช้งาน"** พร้อมคำอธิบายว่าชื่อยังอยู่ในประวัติ และเปิดบัญชี
  ใหม่ให้คนเดิมได้ตลอด · ยังยืนยันก่อนทำเหมือนเดิม
- `PolicyCard` ไม่เปลี่ยน

### `/employees` — Employee

- เพิ่มคอลัมน์ **"บัญชีเข้าใช้งาน"**: ชื่อผู้ใช้ + ป้ายสิทธิ์ หรือป้าย `ยังไม่มีบัญชี` ·
  ไม่มีลิงก์ในแถว (ตารางนี้ไม่เคยมี) แต่มีลิงก์ไป `/users` บนหัวการ์ด
- ข้อความยืนยันตอนปิดใช้งานเพิ่มประโยค: บัญชีเข้าใช้งานของคนนี้จะถูกปิดตามด้วย · และเมื่อเปิด
  กลับต้องไปเปิดบัญชีเองที่หน้าผู้ใช้และสิทธิ์
- ฟอร์มเพิ่มพนักงานไม่เปลี่ยน — การให้สิทธิ์ยังเป็นการกระทำแยกโดยตั้งใจ

## ตัวนำเข้าจาก Access — `api/cli/import-access.php`

ตัวนำเข้าล้าง `employees` ทิ้งแล้วใส่ใหม่ด้วย id ของ Access ทุกครั้ง งานนี้จึงทำให้มันพัง
สองทางถ้าไม่แก้: บรรทัด 302 `UPDATE admins SET employee_id = NULL` ล้มทันทีที่คอลัมน์เป็น
NOT NULL และการล้างตารางจะทิ้งบัญชีให้ชี้ไปยังพนักงานที่ไม่มีอยู่

แก้เป็น:

1. ก่อนล้าง — เก็บ snapshot ในหน่วยความจำ: `admins.id` → (`employee_name`, `first_name`,
   `last_name`, `sex`, `birth_date`, `roles`) ของพนักงานที่บัญชีนั้นผูกอยู่
2. ลบบรรทัด `UPDATE admins SET employee_id = NULL` ทิ้ง (`FOREIGN_KEY_CHECKS = 0`
   เปิดอยู่แล้วตลอดบล็อกนี้ การล้างจึงยังทำได้)
3. หลังใส่พนักงานชุดใหม่จาก Access — ผูกกลับด้วย `employee_name` ที่ตรงกันแบบเป๊ะ
4. บัญชีที่หาคู่ไม่เจอ — สร้างแถวพนักงานคืนจาก snapshot (ได้ id ใหม่เหนือช่วงของ Access)
   แล้วผูก · จบขั้นนี้ต้องไม่มี `admins` แถวไหนที่ `employee_id` ชี้ไปยัง id ที่ไม่มีอยู่
5. พนักงานจาก Access ที่ยังไม่มีแถวเงา — สร้างให้ (คำสั่งเดียวกับขั้นที่ 2 ของ migration)
6. ก่อน `commit()` — ตรวจว่ายังไม่มีแถวกำพร้า ถ้ามีให้ `throw` เพื่อให้ rollback ทั้งชุด

## เทสต์

### `stock/api/tests/50-users.test.php`

เทสต์เดิมสร้างผู้ใช้ด้วย `Users::create()` ตรง ๆ — ต้องแก้ให้สร้างพนักงานก่อนแล้วเรียก
`ensureFor()` + `grantAccount()` เคสใหม่ที่ต้องมี:

- สร้างบัญชีให้ `employee_id` ที่ไม่มีอยู่ → ปฏิเสธ
- สร้างบัญชีให้พนักงานที่ลาออกแล้ว → ปฏิเสธ
- สร้างบัญชีให้พนักงานที่มีบัญชีอยู่แล้ว → ปฏิเสธ
- INSERT `admins` โดยไม่ใส่ `employee_id` → ฐานข้อมูลปฏิเสธ (พิสูจน์ว่ากฎอยู่ที่ฐาน ไม่ใช่โค้ด)
- `syncFromEmployee(active: false)` → `is_active` ของบัญชีเป็น 0 และ `Auth::login()` ล้ม
- `syncFromEmployee(active: true)` ต่อจากนั้น → บัญชี **ยังปิดอยู่**
- ปิดพนักงานที่เป็นเจ้าของร้านที่ใช้งานได้คนสุดท้าย → ปฏิเสธ และพนักงานต้องไม่ถูกปิด
- ปิดพนักงานของตัวเอง → ปฏิเสธ
- `revokeAccount()` → `username` และ `password_hash` เป็น NULL แต่แถวยังอยู่ และ
  `inventory_logs` ที่ชี้มายังอ่านชื่อได้

## สิ่งที่งานนี้ไม่ทำ

- ไม่ย้าย API ผู้ใช้จาก `/stock-api` มาฝั่งหน้าร้าน — ที่ย้ายคือหน้าจอ ไม่ใช่กฎ
- ไม่แตะตารางสิทธิ์ของแต่ละบทบาท (`Roles.php`) — โจทย์คือ "ใครมีบัญชี" ไม่ใช่ "บทบาททำอะไรได้"
- ไม่รวมหน้า `/users` กับ `/employees` เข้าด้วยกัน
- ไม่แก้ `sales.employee_id` / `case_events.employee_id` ให้ชี้ `admins` — ทั้งสองชี้
  `employees` ซึ่งตอนนี้เป็นข้อมูลหลักแล้ว จึงถูกอยู่
