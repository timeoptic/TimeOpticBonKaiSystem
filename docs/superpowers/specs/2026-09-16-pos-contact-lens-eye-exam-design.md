# ขายคอนแทคเลนส์ใน POS พร้อมวัดสายตา — Design (ทาง 3: ไม่แตะ DB, ไม่แตะ Process หลัก)

วันที่: 2026-09-16 · สถานะ: รอผู้ใช้ตรวจ spec · ห้าม implement จนกว่าจะอนุมัติ

แทนที่ฉบับ `2026-09-15-pos-contact-lens-eye-exam-design.md` ทั้งฉบับ (ฉบับนั้นสร้างตาราง `eye_exams` + เพิ่ม 2 คอลัมน์ — ผู้ใช้ตัดออกเมื่อ 16 ก.ย.)

## 1. เป้าหมาย

- ขายคอนแทคเลนส์ใน POS โดยเลขอ้างอิงคือ `POS-2026-xxxxx` ไม่เปิด `CASE-…`
- ขายแยกข้างซ้าย/ขวาได้ต่อกล่อง
- ค่าของกล่องคอนแทคเลนส์ **พนักงานกรอกเอง** ระบบไม่เติมให้อัตโนมัติ
- วัดสายตาที่ POS ได้ และผลวัด **เข้าประวัติค่าสายตาของลูกค้า** ดูย้อนหลังได้จากหน้าลูกค้า
- บิล POS อ้างอิงได้ว่าใช้ค่าสายตาใบไหน วัดวันไหน

## 2. ข้อกำหนดจากผู้ใช้ (16 ก.ย. 2026) — เป็นกรอบบังคับ

1. **ห้ามเปลี่ยน schema ของฐานข้อมูล** — ไม่มีตารางใหม่ ไม่มีคอลัมน์ใหม่ ไม่มี ALTER TABLE
2. **ห้ามแตะ Process หลัก** — ขั้นตอน 6 ขั้นของเคสตัดแว่นและหน้าจอที่พนักงานเห็นต้องเหมือนเดิม
3. **ห้ามเพิ่ม `Contact Lens` ใน Test For และห้ามแก้ Lookup** — หน้าวัดสายตาของเคสไม่ต้องรู้จักคำว่าคอนแทคเลนส์
4. **คอนแทคเลนส์เป็นเรื่องของ POS** — ระบบรู้ว่าการวัดครั้งนั้นเพื่อคอนแทคเลนส์จากฝั่ง POS ที่เป็นต้นทาง
5. ผลวัดจาก POS ต้องเก็บเป็นประวัติของลูกค้าด้วย

## 3. ไม่อยู่ในขอบเขตรอบนี้

- รูปถ่ายตอนวัดที่ POS (API แนบรูปผูกกับเคสเท่านั้น)
- พิมพ์ค่าสายตาบนใบเสร็จ POS (ใบเสร็จไม่อ่าน `item_meta` อยู่แล้ว)
- เคส "ตรวจสายตาอย่างเดียว" แบบขั้นตอนสั้น — spec แยกทีหลัง
- ตัดสต็อกคอนแทคเลนส์ (POS ไม่ตัดสต็อกอยู่แล้ว)
- บิลร่างฝั่ง server

## 5. การตัดสินใจหลัก

1. **POS มีฟอร์มวัดสายตาเล็กของตัวเอง** — เพราะไม่มีหน้าวัดนอกเคสให้เปิด และ `ExamPanel` ผูกกับเคสแน่น การไปแก้มันคือการแตะ Process หลัก ซึ่งข้อกำหนดข้อ 2 ห้ามไว้
2. **ฟอร์มนั้นเขียนแถว `prescriptions` ธรรมดา 1 แถว** — `case_id = NULL`, `kind = 'final'`, `source = 'contact_lens'`, มี `customer_id` → หน้าตาเหมือนข้อมูลเก่า 8,401 แถวที่มีอยู่แล้ว
   (ร่างแรกเขียนว่า `'pos'` — เปลี่ยนตอนลงมือเพราะ `RX_SOURCE_LABEL` ใน `RxSets.jsx:23` รู้จัก `contact_lens` อยู่แล้วและแปลป้ายให้เป็น "จากคอนแทคเลนส์" · ความหมายตรงกว่าด้วย: บอกว่าวัดเพื่ออะไร ไม่ใช่วัดที่เครื่องไหน)
3. **ไม่เรียก `/confirm`** — `kind='final'` เขียนตรงจาก POST ได้เลย จึงไม่เดินผ่านด่าน `test_for` → ข้อกำหนดข้อ 3 ไม่ถูกละเมิด และ Lookup ไม่ถูกแตะ
4. **บิลผูกกับใบวัดผ่าน `item_meta.rx_id`** ต่อรายการ ไม่ใช่ต่อบิล — ซื้อสองกล่องคนละใบวัดได้ และตรงกับที่ `item_meta` ถูกออกแบบมา
5. **ข้างของกล่องเป็น `pos_fields` แบบตัวเลือก** — ตะกร้าแยกแถว R/L ให้เองเพราะ `item_meta` ต่างกัน
6. **กันรั่วด้วย `source='contact_lens'` ที่ `caseDetail`** — จุดเดียว บรรทัดเดียว

## 6. Database — ไม่มีการเปลี่ยน schema

**ไม่มี** `CREATE TABLE` · **ไม่มี** `ALTER TABLE` · **ไม่มี** คอลัมน์ใหม่ · **ไม่มี** FK ใหม่

มีเพียง **การแก้ข้อมูล** หนึ่งรายการ: เพิ่มช่อง `eye` เข้าไปใน `pos_items.pos_fields` ของคอนแทคเลนส์ทุกตัว

```json
{"key":"eye","label":"ข้าง","type":"choice","required":true,
 "options":[["R","ขวา (R)"],["L","ซ้าย (L)"],["RL","ทั้งสองข้าง"]]}
```

- ใส่ **ก่อน** `power` ในลิสต์ · `Maxim color` คงช่อง `color` ไว้
- เป้าหมาย: แถวที่ `group_code LIKE 'PosCtl%'` และยังไม่มีคีย์ `eye`
- เขียนเป็นไฟล์ SQL ในระบบเลขของ `stock/api/migrations/` ตามแบบเดิม (มีแต่ `UPDATE` / `INSERT … ON DUPLICATE KEY UPDATE` ไม่มี DDL) รันซ้ำได้ไม่พัง
- **ห้ามจองเลข 037 ล่วงหน้า** — ตอนนี้ `034`–`036` ยังไม่ commit (งาน session อื่น) ต้องเลือกเลขจริงตอนลงมือหลังเช็ก `git status` และ `ls` ใหม่
- `type` ที่ไม่ระบุ = ช่องข้อความแบบเดิม ของเดิมทุกตัวจึงไม่ต้องแก้

## 7. API — แก้ 2 จุด ไม่มี endpoint ใหม่

| Route | การเปลี่ยนแปลง |
|---|---|
| `caseDetail()` `cases.php` | เติมเงื่อนไข: แถวไม่ผูกเคสที่ดึงมาต้อง `(p.source IS NULL OR p.source <> 'contact_lens')` — กันใบที่วัดจาก POS ไหลเข้าเคสและทำให้ขั้นวัดสายตาขึ้นเสร็จเอง · **ทำแล้ว 16 ก.ย. 2026** หลังเกิดจริงกับ CASE-2026-00002 (เคยเลื่อนไว้เพราะไฟล์นี้มี session อื่นแก้ค้าง — การเลื่อนนั้นเป็นการตัดสินใจที่ผิด) |
| `POST /api/pos/sales` `pos.php:349-354` | เพิ่มการตรวจช่อง `type='choice'`: ค่าที่ส่งมาต้องอยู่ใน `options` ไม่งั้น 400 · ช่องแบบเดิมตรวจเหมือนเดิมทุกประการ |

**ไม่ต้องสร้าง endpoint ใหม่เลย** — ของเดิมพอ:

- ค้นลูกค้า: `GET /api/customers?q=` (`customers.php:5-22`)
- ผลวัดล่าสุด: `GET /api/customers/:id/exam-sessions` (`prescriptions.php:268`) แล้วหยิบรอบแรกที่มี `final`
- บันทึกผลวัด: `POST /api/prescriptions` (`prescriptions.php:109`)
- อ่านใบวัดกลับมาแสดง: `GET /api/prescriptions/:id` (`prescriptions.php:57`)
- แนบลูกค้าเข้าบิล: `customer_id` ใน `POST /api/pos/sales` (มีอยู่แล้ว)

## 8. Frontend

### 8.1 หน้า POS `app/(frontdesk)/pos/page.jsx`

- **ตัวเลือกลูกค้า** (ไม่บังคับ) ใช้ `Picker.jsx` + `/api/customers` — ช่องชื่อ/เบอร์พิมพ์เองยังอยู่ เลือกแล้วเติม snapshot ให้
- **แผง "ค่าสายตาสำหรับคอนแทคเลนส์"** แสดงเมื่อตะกร้ามีรายการที่ `pos_fields` มีคีย์ `power`
  - ยังไม่เลือกลูกค้า → "เลือกลูกค้าเพื่อใช้ค่าสายตา" (ขายต่อได้โดยไม่แนบ)
  - เลือกแล้ว → โหลด `exam-sessions` ครั้งเดียวต่อลูกค้า
  - ปุ่ม **ใช้ผลวัดล่าสุด** · **วัดสายตาใหม่** (เปิด dialog ข้อ 8.2) · **ไม่แนบค่าสายตา**
  - แนบแล้ว: ตาราง R/L ย่อ + วันที่วัด + ปุ่มเปลี่ยน
- **แต่ละกล่องคอนแทคเลนส์**: ช่อง "ข้าง" (ปุ่มเลือก R / L / ทั้งสองข้าง) + ช่อง "ค่าสายตา" กรอกเอง · ถ้ามีใบวัดแนบอยู่ แสดงค่าของข้างที่เลือกเป็น**ข้อความอ้างอิงใต้ช่อง** ไม่เติมให้

### 8.2 `components/pos/PosExamDialog.jsx` (ใหม่)

ฟอร์มเล็กของ POS เอง — **ไม่ใช่** `ExamPanel` และไม่ import มัน

- บันทึก → `POST /api/prescriptions` ด้วย `{customer_id, case_id: null, kind:'final', source:'contact_lens', test_date, performed_by, r_*, l_*}`
- **ไม่เรียก `/confirm`** → `confirmed_at` เป็น NULL, `test_for` ไม่ถูกบังคับ, Lookup ไม่ถูกแตะ

## 9. Flow

```
POS เพิ่มคอนแทคเลนส์ → (เลือกลูกค้า) → แผงค่าสายตา
  ├─ ใช้ผลวัดล่าสุด ──────────────┐
  ├─ วัดสายตาใหม่ → PosExamDialog ─┤→ ได้ rx_id
  └─ ไม่แนบ ─────────────────────┘
→ กรอกข้าง + ค่าสายตาต่อกล่อง → รับเงิน → POST /api/pos/sales
   (item_meta = {eye, power, rx_id})
```

ผลวัดเข้าประวัติลูกค้าทันทีที่กดบันทึกใน dialog ถึงลูกค้าจะไม่ซื้อก็ยังเป็นประวัติ

## 10. ผลกระทบและการกัน

- **เคสตัดแว่น**: ไม่แตะเลยสักไฟล์ ยกเว้น WHERE เดียวใน `caseDetail` ที่**กัน**ของใหม่ไม่ให้ไหลเข้า — ต้องมี e2e ก่อน/หลังยืนยันว่าขั้นวัดสายตาในเคสส่ง request เดิมและเห็นแถวเดิม
- **`ExamPanel` / Lookup / Test For**: ไม่ถูกแก้แม้แต่บรรทัดเดียว
- **POS ทั่วไป**: ไม่เลือกลูกค้า ไม่เห็นแผงค่าสายตา · ไม่ส่ง `customer_id`/`rx_id` = พฤติกรรมเดิม 100%
- **หนี้ที่รับไว้อย่างรู้ตัว**:
  1. `source` แบกสองความหมาย (ได้ค่ามายังไง + วัดเพื่ออะไร) · `ExamPanel.jsx:331-332` จัดประเภทแถวด้วย `source` — ค่า `'contact_lens'` จะตกไปเป็น `measured` แต่แถวเหล่านี้ถูกกันออกจาก `caseDetail` แล้วจึงไม่ไปถึง ExamPanel · **มีเทสต์ยืนยันแล้ว** ที่ `api/tests/22-case-type-processes.test.php`
  2. `rx_id` ใน JSON ไม่มี FK — ลบใบวัดแล้วชี้ไปที่ว่างเงียบ ๆ
  3. ค้นย้อน "บิลไหนใช้ใบนี้" ต้องไล่อ่าน JSON (MariaDB 10.4 ใช้ `JSON_UNQUOTE(JSON_EXTRACT())` เท่านั้น) — ยอมรับได้ที่ปริมาณข้อมูลปัจจุบัน
  4. ใบจาก POS มี `confirmed_at` เป็น NULL — ถ้าวันหน้ามีรายงานที่นับเฉพาะใบยืนยันแล้ว ต้องตัดสินใจอีกที
  - ทั้ง 4 ข้อแก้ทีหลังได้ด้วยการ**เพิ่ม**คอลัมน์ ซึ่งยังเป็น additive เหมือนเดิม ไม่ได้ยากขึ้นเพราะเลือกทางนี้ก่อน
- **Performance**: ประวัติ POS ไม่เพิ่ม query · detail +1 PK lookup เฉพาะบิลที่มี `rx_id` · หน้า POS +1 query เฉพาะตอนมีคอนแทคเลนส์และเลือกลูกค้า

  - `caseDetail` ไม่ดึงแถว `source='contact_lens'` และขั้นวัดสายตาของเคสไม่ขึ้นเสร็จจากใบ POS · **ต้องคู่กับเทสต์ที่ยืนยันว่าใบเก่าไม่ผูกเคส (`source` เป็น NULL) ยังถูกดึงเข้าเหมือนเดิม** ไม่งั้นแก้ปัญหาเล็กแล้วทำข้อมูล Access 8,401 ใบหายไปจากเคส
  - `caseDetail` **ยัง**ดึงแถวไม่มีเคสของเดิม (`source` อื่นหรือ NULL) เหมือนเดิม — กัน regression กับข้อมูล Access 8,401 แถว
  - `POST /api/prescriptions` รับ `source='contact_lens'` + `case_id` ว่าง ได้ `kind='final'` โดยไม่ต้องมี `test_for`
  - `POST /api/pos/sales`: ช่อง choice ค่านอก `options` = 400 · ไม่ส่ง `customer_id`/`rx_id` = เหมือนเดิม · `item_meta` เก็บ `eye`/`rx_id` ครบ
  - `examSessions` คืนรอบจาก POS เป็นรอบของตัวเอง
- **Lib (node --test)**: helper เลือกค่าอ้างอิงตามข้าง R/L/RL · `cart.js` แยกแถวเมื่อ `eye` ต่างกัน (เพิ่มเคสใน `posCart.test.js`)
- **E2E (Playwright, mock API)**: บิลทั่วไปไม่เปลี่ยน · คอนแทคเลนส์ R/L แยกแถว · วัดสายตาใน dialog แล้วตะกร้ายังอยู่ · ขั้นวัดสายตาในเคสส่ง request เดิม · `buttons.spec` / `mobile.spec` ผ่าน

## 12. ลำดับงาน (รายละเอียดใน implementation plan)

1. เทสต์ baseline ของเดิม (`caseDetail`, `processMissing`, `examSessions`, e2e ขั้นวัดสายตาในเคส) — ต้องเขียวก่อนแตะอะไร
2. กันรั่วที่ `caseDetail` + เทสต์คู่ (กันของใหม่ / ไม่กันของเก่า)
3. ไฟล์ SQL แก้ข้อมูล `pos_items` (เลือกเลขตอนลงมือ) + ตรวจ `type=choice` ใน `pos.php`
4. `CartItemRow` รองรับ choice + เทสต์ตะกร้า
5. `PosExamDialog` + แผงค่าสายตาในหน้า POS + ตัวเลือกลูกค้า
6. แสดงผล (`pos/detail`, `print/prescription`, `manual`)

Deploy ทีละขั้น: ข้อมูล `pos_items` (dry-run ก่อน) → API → หน้าเว็บ ตามวิธีเทียบ chunk + md5 guard เดิม · `/cases/detail/` มี session อื่นแก้บ่อย ต้องเช็ก `git status` และ build id ของ live ก่อนขึ้นทุกครั้ง

## 13. ที่ยังไม่ตัดสิน — ขอผู้ใช้ยืนยันตอนตรวจ spec

1. ช่อง "ข้าง" **บังคับกรอก** สำหรับคอนแทคเลนส์ทุกตัว — ใช่หรือไม่
2. ฟอร์มวัดของ POS เก็บแค่ R/L SPH·CYL·AXIS·ADD·VA พอไหม ต้องมีช่องอื่นอีกหรือเปล่า
3. ใบที่วัดจาก POS ไม่มีสถานะ "ยืนยันแล้ว" — ถ้าอยากให้มี ต้องคุยเรื่อง `test_for` ใหม่
4. ถ้าลูกค้าซื้อคอนแทคเลนส์โดยไม่เลือกลูกค้าในระบบ = ขายได้แต่ไม่มีประวัติ — ยอมรับได้ใช่ไหม
