# เคส "ตรวจสายตาอย่างเดียว" — ขั้นตอนตามประเภทงาน (Design)

วันที่: 2026-09-16 · สถานะ: รอผู้ใช้ตรวจ spec · ห้าม implement จนกว่าจะอนุมัติ

## 1. เป้าหมาย

- ลูกค้ามาตรวจสายตาอย่างเดียว ต้องมีขั้นตอนแค่ **รับลูกค้า → วัดสายตา → จบ**
- ยืนยันผลวัดแล้ว **เคสปิดเอง** (`status = completed`, `closed_at` มีค่า)
- **1 Case = 1 งาน** — ห้ามเอาเคสตรวจสายตาไปต่อเป็นเคสตัดแว่น
- อยากตัดแว่นทีหลัง = **เปิดเคสใหม่ประเภท "ตัดแว่นใหม่"** แล้วดึง Final Rx จากเคสเดิมมาอ้างอิงได้ · เคสเดิมยังคง `completed` เหมือนเดิม
- ประวัติการวัดสายตาย้อนหลังต้องอยู่ครบ

## 2. ข้อกำหนดจากผู้ใช้ (16 ก.ย. 2026)

1. ประเภทงานเป็นตัวกำหนดว่าเคสมีขั้นตอนอะไรบ้าง
2. ยืนยันผลวัดแล้วปิดเคสอัตโนมัติ — **ไม่ต้องมีปุ่ม "จบเคส" แยก**
3. ห้ามเปลี่ยนเคสตรวจสายตาเป็นเคสตัดแว่น
4. แก้ค่าสายตาหลังเคสปิดแล้ว ให้เคส**คงสถานะปิดไว้ตามเดิม** ไม่ต้องเปิดกลับ

## 4. การตัดสินใจหลัก

1. **กฎ "ประเภทงาน → ขั้นตอน" อยู่ที่เดียว** ใน `Lookups.php` ข้าง `case_type`

   | ประเภทงาน | ขั้นตอน |
   |---|---|
   | ตรวจสายตา | `reception`, `exam` |
   | ตัดแว่นใหม่ / เปลี่ยนเลนส์ / ซ่อม-ปรับแว่น / ไม่ระบุ | ครบ 6 ขั้นเหมือนเดิม |

2. **ปิดเคสเองโดยไม่ต้องเขียนกลไกใหม่** — พอ `exam` เป็นขั้นสุดท้ายของรายการ การยืนยันผลวัดทำให้ `advanceCaseStatus()` ไม่เหลือขั้นถัดไป → ตั้ง `completed` → `setStatus()` เซ็ต `closed_at` ให้เอง
3. **server เป็นเจ้าของกฎ** — `caseDetail` ส่ง `process_list` ไปด้วย ฝั่ง JS เลิกถือกฎเอง เหลือแค่ป้าย/สี/ไอคอน (แก้กับดักค่าคงที่สองที่)
4. **แก้หลังปิดแล้ว เคสยังปิดอยู่** — ไม่ไปแตะกฎ "ไม่ถอยเคสกลับ" (`processes.php:257-258`) ซึ่งเป็นกฎกลางที่เคสตัดแว่นทุกใบใช้ร่วมกัน · ไทม์ไลน์บันทึกการแก้ไว้อยู่แล้ว
5. **ไม่แตะ schema** — ไม่มีตารางใหม่ ไม่มีคอลัมน์ใหม่

## 6. ไม่อยู่ในขอบเขตรอบนี้

- เปลี่ยนป้าย "แว่นเดิม" ตอนดึง Final Rx จากเคสก่อน (ค่า `prev_exam` ใน `OLD_SOURCES`) — ของเดิมใช้งานได้แล้ว รอดูว่าป้ายกวนใจจริงไหมค่อยทำ
- ขั้นตอนสั้นของ "ซ่อม/ปรับแว่น" และ "เปลี่ยนเลนส์" — โครงนี้รองรับแล้ว แต่ต้องให้ร้านบอกก่อนว่าแต่ละงานมีขั้นอะไร
- ย้อนแก้ข้อมูลเคสเก่า

## 7. ผลกระทบและการกัน

- **เคสตัดแว่น**: `processesFor()` คืนครบ 6 ขั้นเหมือนเดิมทุกใบ → พฤติกรรมไม่เปลี่ยน ต้องมีเทสต์ยืนยัน
- **ข้อมูลเก่า**: เคสที่ `case_type` ว่าง/ไม่รู้จัก ได้ครบ 6 ขั้น
- **รายงาน**: `case_type` เป็นมิติจัดกลุ่ม เคสตรวจสายตาโผล่เป็นแถวรายได้ 0 ไม่ทำให้ตัวเลขเดิมเพี้ยน
- **คิวส่งมอบ**: กรอง `is_terminal = 0` อยู่แล้ว เคสที่ปิดไม่ไปโผล่
- **ความเสี่ยงที่รับไว้**: ถ้าเปิดเคสตรวจสายตาผิดประเภท จะปิดเองตั้งแต่วัดเสร็จ · แก้โดยเปิดเคสใหม่ให้ถูกประเภท ซึ่งตรงกับกติกา "1 Case = 1 งาน" อยู่แล้ว

## 8. การทดสอบ

- **API (`api/tests`)**
  - `processesFor()`: ตรวจสายตา = 2 ขั้น · ตัดแว่นใหม่ = 6 ขั้น · ว่าง/ไม่รู้จัก = 6 ขั้น
  - เคสตรวจสายตา: ยืนยัน `exam` แล้ว `status = completed` และ `closed_at` ไม่ว่าง
  - เคสตัดแว่น: ยืนยัน `exam` แล้ว **ยังไม่ปิด** (กัน regression ของงานหลัก)
  - `caseDetail` คืน `processes` เฉพาะขั้นของเคสนั้น และมี `process_list`
  - ยิง `POST /processes/sales/start` ใส่เคสตรวจสายตา = 400
  - `reopen` ขั้น `exam` ของเคสที่ปิดแล้ว ยังทำได้ และเคสยังคง `completed`
- **E2E (mock API)**: เคสตรวจสายตาเห็น 2 ขั้น · เคสตัดแว่นเห็น 6 ขั้นเท่าเดิม · เปิด `?step=sales` ของเคสตรวจสายตาแล้วตกมาหน้าภาพรวม

## 9. ลำดับงาน

1. เทสต์ baseline ของเคสตัดแว่น (ยืนยันทีละขั้นจนจบ) — ต้องเขียวก่อนแตะอะไร
2. `processesFor()` + เทสต์ของมันเอง
3. ต่อเข้า `processes.php` 4 จุด + เทสต์เคสตรวจสายตาปิดเอง
4. `caseDetail` ส่ง `process_list` + เทสต์
5. หน้าเว็บ: stepper, `?step=` guard, ตัวนับกระดาน, ข้อความหน้าเปิดเคส
6. e2e
